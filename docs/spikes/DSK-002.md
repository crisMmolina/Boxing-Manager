# DSK-002 · Spike: servidor WebSocket en Windows 11 + firewall + jpackage

Fecha: 2026-10-25 · Máquina: Windows 11 Home, JDK 25.0.5 (Oracle), Wi-Fi `Public` en 192.168.100.22.

## Resumen

| Pregunta | Resultado |
|---|---|
| Javalin 7 sirve un WS de eco en 8765 | **Verificado** (Javalin 7.2.3, Jetty 12.1.12) |
| Accesible desde un teléfono por el hotspot | **No verificado**: no hubo teléfono. Solo se probó `localhost` y la IP LAN desde la misma PC |
| Regla de firewall | Comando abajo. **No se ejecutó** (requiere admin y modifica la configuración de seguridad) |
| jpackage genera `.msi` | **No en esta máquina**: falta WiX. Error exacto abajo |
| jpackage genera app-image con `.exe` sin Java instalado | **Verificado** (128 MB, el `.exe` arranca y responde el eco) |
| Respaldo Java-WebSocket | **No hizo falta**: Javalin funcionó, no se registró `uak decision` |

## 1. Javalin 7 WS en 8765

Dependencias: `io.javalin:javalin:7.2.3` + `org.slf4j:slf4j-simple:2.0.16`. Trae Jetty 12.1.12.

En 7.2.3 los endpoints se declaran dentro de `Javalin.create(cfg -> cfg.routes...)` (así compiló y corrió).

```java
Javalin.create(cfg -> cfg.routes.ws("/ws", ws -> {
    ws.onConnect(ctx -> System.out.println("connect " + ctx.sessionId()));
    ws.onMessage(ctx -> ctx.send("echo:" + ctx.message()));
})).start("0.0.0.0", 8765);
```

Hay que enlazar a `0.0.0.0` (no `localhost`) para que un teléfono llegue. `netstat -ano` mostró `0.0.0.0:8765 LISTENING`.

Prueba (cliente `java.net.http.WebSocket` del JDK, sin dependencias):

- `ws://localhost:8765/ws` → `echo:hola`
- `ws://192.168.100.22:8765/ws` → `echo:hola`

Límite de la prueba: conectar a la propia IP LAN desde la misma PC no pasa por el firewall de entrada, así que **no demuestra** que un teléfono llegue. Esa prueba queda pendiente (ver §5).

Notas de build: con JDK 25 y Maven 3.9.9 compila con `maven.compiler.release=25`. El `JAVA_HOME` de esta PC apuntaba a un `jdk-24.0.2` que ya no existe; hay que corregirlo para Maven. El repo usa Gradle 8.2 (wrapper), que no corre en JDK 25: DSK-001 tendrá que subir el wrapper.

## 2. Regla de firewall (Windows 11)

Perfil activo de esta PC: **Public** (`Totalplay-2CB8-5G`, Wi-Fi). Con `BlockInbound` por defecto en Public, el teléfono no entra sin regla. No se confió en el aviso interactivo "Permitir acceso" de Windows (no se observó aquí): la regla debe crearse de forma explícita al instalar.

Comando exacto (PowerShell o `cmd` **como administrador**):

```bat
netsh advfirewall firewall add rule name="BoxCentral WS 8765" dir=in action=allow protocol=TCP localport=8765 profile=any
```

Para quitarla:

```bat
netsh advfirewall firewall delete rule name="BoxCentral WS 8765"
```

Se abre por puerto y no por programa para que sirva igual con el `.exe` instalado o con `java` suelto. `profile=any` cubre Public, Private y Domain porque no se sabe qué categoría le asigna Windows al hotspot.

Estado: **comando no ejecutado ni probado**. Esta PC ya tenía reglas de entrada para `java`/`javaw` en Public (de otras instalaciones), así que una prueba aquí no distinguiría el efecto de la regla nueva.

## 3. jpackage (JDK 25)

`jpackage 25.0.5` está en el `PATH`.

### `.msi`: requiere WiX

Salida exacta de `jpackage --type msi ...`:

```
Can not find WiX tools. Was looking for WiX v3 light.exe and candle.exe or WiX v4/v5 wix.exe and none was found
Download WiX 3.0 or later from https://wixtoolset.org and add it to the PATH.
```

Requisito: WiX v3 (`candle.exe` + `light.exe`) o WiX v4/v5 (`wix.exe`) en el `PATH` de quien construye. **No se instaló WiX** (no hubo autorización para instalar software). El `.msi` queda **sin generar ni verificar**. Quien lo construya necesita WiX; quien lo instale (el cliente) no necesita nada.

### app-image: funciona sin WiX

```
jpackage --type app-image --name BoxCentralSpike --input jp-in --main-jar echo-1.0.0.jar --main-class spike.Main --dest jp-out/img --app-version 1.0.0
```

Resultado: carpeta `BoxCentralSpike/` con `BoxCentralSpike.exe`, `app/` y `runtime/` (JRE embebido), **128 MB**. Se ejecutó el `.exe` y respondió `echo:hola` por `ws://localhost:8765/ws`: corre sin Java instalado. Sirve como plan B comprimido en `.zip` si WiX no está.

Trampas encontradas:

- `--class-path` **no existe** en jpackage (`Invalid Option`). Todas las jars deben ir **planas** en la carpeta `--input` y jpackage arma el classpath con ellas. Con las jars en un subdirectorio `lib/` no se incluyen.
- Sin `--type`, o con `--type msi` sin WiX, jpackage falla antes de construir nada: probar `--type app-image` primero.
- 128 MB es el JRE completo. Reducirlo con `--add-modules` (o `jlink`) **no se probó**.

## 4. Decisión sobre el respaldo

Javalin 7.2.3 cumplió el criterio de eco, así que no se registra respaldo Java-WebSocket con `uak decision`. Ese respaldo solo se activaría si la prueba con teléfono (§5) falla por causa de Javalin y no del firewall.

## 5. Pendiente para cerrar el spike

1. Con el hotspot encendido y un teléfono conectado: correr el `.exe` (o el jar), crear la regla de §2 como admin, abrir `ws://<IP del hotspot>:8765/ws` desde el teléfono y confirmar el eco. Probar también **sin** la regla para confirmar que el firewall bloquea.
2. Instalar WiX y repetir `jpackage --type msi`; anotar versión de WiX y tamaño del `.msi`.
3. Confirmar la categoría de red (Public/Private) que Windows da al adaptador del hotspot.
